# Project 1: Secure File Encryption and Tamper Detection

A small C++17 command-line application that uses OpenSSL's EVP API and
AES-256-GCM authenticated encryption. It never writes decrypted bytes until the
GCM authentication tag has been verified.

## Requirements

- C++17 compiler
- CMake 3.16 or newer
- OpenSSL development files (OpenSSL 1.1.1 or 3.x)

On MSYS2 UCRT64, install the tools with:

```sh
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake \
  mingw-w64-ucrt-x86_64-openssl mingw-w64-ucrt-x86_64-ninja
```

## Build on Windows (MSYS2 UCRT64)

Open an **MSYS2 UCRT64** terminal in this directory:

```sh
cmake -S . -B build -G Ninja
cmake --build build
```

The executable is `build/crypto.exe`.

## Commands

```text
crypto encrypt input.txt encrypted.bin key.bin
crypto decrypt encrypted.bin key.bin output.txt
crypto test
```

Existing output files are not overwritten unless the user explicitly answers
`y` at the prompt. `key.bin` is raw secret key material and must be protected.

## Encrypted binary layout

All offsets are byte offsets. The ciphertext length is determined from the file
size.

| Offset | Length | Meaning |
|---:|---:|---|
| 0 | 8 | Magic/version: `SFEGCM1\0` |
| 8 | 12 | Fresh 96-bit GCM nonce |
| 20 | variable | Ciphertext (same length as plaintext) |
| end - 16 | 16 | 128-bit GCM authentication tag |

The minimum valid encrypted-file length is therefore 36 bytes. The parser
checks the header and minimum length, and the key file must be exactly 32 bytes.

## Security notes

- A new random key and nonce are generated by `RAND_bytes()` for every normal
  encryption command.
- AES-GCM provides confidentiality and authentication. A wrong key or any
  modification to the ciphertext or tag causes decryption to fail.
- Candidate plaintext exists only in memory and is discarded when
  authentication fails; the output file is written only after success.
- Never reuse a nonce with the same GCM key. The test command demonstrates that
  reuse reveals the XOR relationship between plaintexts and explains the
  related forgery risk.

## Automated validation

Run:

```sh
build/crypto.exe test
```

It reports PASS/FAIL for ciphertext tampering, tag modification, a wrong-key
attack, nonce-reuse analysis, and correctness recovery. See `TEST_RESULTS.txt`
for the captured run and `REPORT.md` for the experiment discussion.

The included `sample_encrypted.bin` and `sample_key.bin` are demonstration
artifacts only. Never use demonstration keys for real data.
